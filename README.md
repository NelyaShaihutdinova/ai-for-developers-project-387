## Кратко о приложении

Сервис позволяет владельцу календаря заранее завести несколько типов встреч и принимать записи от гостей без регистрации. Гость выбирает тип встречи, видит свободные слоты на ближайшие 14 календарных дней и бронирует удобное время. Один и тот же интервал нельзя занять дважды, даже если типы встреч разные.

## Роль владельца

В приложении есть один заранее заданный владелец календаря.

### Сценарий владельца

1. Владелец открывает административный раздел приложения.

2. Владелец создаёт тип встречи.

3. Для типа встречи заполняются:
   - название;
   - описание;
   - длительность.

4. После сохранения тип встречи появляется в общем каталоге доступных встреч.

5. Владелец может создать несколько типов встреч с разной длительностью, например 15 минут и 30 минут.

6. Владелец открывает список предстоящих встреч и видит все созданные бронирования независимо от типа встречи.

7. Когда гость записывается на свободный слот, новая запись появляется в списке предстоящих встреч владельца.

## Роль гостя

Гость пользуется сервисом без регистрации и без личного кабинета.

### Сценарий гостя

1. Гость открывает главную страницу сервиса.
2. Гость переходит к списку типов встреч.
3. Гость выбирает подходящий тип встречи по названию, описанию и длительности.
4. После выбора открывается календарь бронирования.
5. Гость видит доступность только в окне ближайших 14 календарных дней.
6. Гость выбирает день из доступного окна.
7. Сервис показывает свободные стартовые слоты для выбранного дня.
8. Длительность каждого занятого интервала определяется выбранным типом встречи.
9. Гость выбирает свободный слот и подтверждает запись.
10. После успешного бронирования слот становится недоступным для повторной записи.

## Обязательные функции

- Просмотр списка типов встреч.
- Создание типа встречи владельцем.
- Хранение для каждого типа встречи: названия, описания и длительности.
- Просмотр календаря доступных слотов для выбранного типа встречи.
- Ограничение окна записи ближайшими 14 календарными днями.
- Создание бронирования гостем без регистрации.
- Просмотр владельцем списка предстоящих встреч всех типов.
- Исключение двойного бронирования одного и того же времени.
- Запрет любых пересечений интервалов, включая частичное наложение между встречами разных типов.
- Корректная обработка одновременных запросов на один слот.

## Ограничения и допущения

- В приложении нет авторизации.
- В приложении нет личных кабинетов.
- В приложении нет интеграции с внешними календарями.
- В приложении только один владелец календаря, он задан заранее.
- Следующая встреча может начинаться ровно в момент окончания предыдущей.
- Начало окна записи, рабочие часы владельца, шаг старта слотов и часовой пояс должны быть зафиксированы позднее в спецификации.
- Данные могут храниться в памяти процесса; если будет выбран этот вариант, в README.md нужно явно указать, что перезапуск сбрасывает записи.

## Требования к API и генерации

- Контракт API должен быть описан через TypeSpec.
- Из TypeSpec должна генерироваться OpenAPI-спецификация.
- Для фронтенда должен генерироваться клиентский SDK из OpenAPI.
- Перед окончательным выбором стека нужно проверить, что для выбранного языка фронтенда существует подходящий генератор клиента.
- Если серверная генерация типов и маршрутов недоступна, бекенд реализуется вручную по контракту и проверяется тестами.

## Агентский воркфлоу (OpenCode)

Репозиторий настроен на вызов ИИ-агента из комментариев GitHub.

### Как вызвать

Оставьте комментарий в issue или PR с одной из команд:

```
/opencode опиши, что нужно сделать
/oc создай спецификацию для этой задачи
```

### Настройки

| Параметр | Значение |
|---|---|
| **События** | `issue_comment`, `pull_request_review_comment` (`created`) |
| **Модель** | `opencode/qwen3.6-plus` (GitHub Secret `OPENCODE_MODEL`) |
| **Авторизация** | GitHub App (id-token: write), без API-ключей |
| **Mentions** | `/opencode`, `/oc` |
| **Назначение** | Анализ issue/PR, генерация спецификаций, планирование задач, реализация кода |
| **Доступ** | Только доверенные участники (OWNER, MEMBER, COLLABORATOR); боты и fork-PR исключены |
| **Параллельность** | Один запуск на issue/PR (concurrency по номеру) |
| **Таймаут** | 30 минут |
| **Share** | Результаты публикуются в комментарий того же issue/PR |

### Где смотреть результаты

- **GitHub Actions**: вкладка [Actions → opencode](https://github.com/NelyaShaihutdinova/ai-for-developers-project-387/actions/workflows/opencode.yml) — логи запуска
- **Комментарий в issue/PR**: агент отвечает текстом с результатом работы

## Автотриаж (Auto-Triage)

Репозиторий автоматически разбирает новые issue при их создании.

### Как работает

1. При создании issue запускается workflow `auto-triage.yml` (событие `issues:opened`)
2. Агент получает инструкцию через встроенный prompt: прочитать описание и обсуждение, проанализировать существующий код, задать уточняющие вопросы, предложить следующий шаг (`to-spec`, `to-tickets` или `wontfix`)
3. Применяет метку триажа из `docs/agents/triage-labels.md`:

| Метка | Значение |
|---|---|
| `needs-triage` | Новый issue, ожидает разбора |
| `needs-info` | Нужны уточнения от автора |
| `ready-for-agent` | Полностью описан, готов к реализации агентом |
| `ready-for-human` | Требует реализации человеком |
| `wontfix` | Не будет реализован |

### Фильтры

- **Доверенные авторы**: только `OWNER`, `MEMBER`, `COLLABORATOR`; fork-PR исключены (`author_association != 'NONE'`)
- **Боты исключены**: `user.type != 'Bot'`
- **Параллельность**: один запуск на issue (`concurrency` по номеру), `cancel-in-progress: false`
- **Таймаут**: 10 минут

### Пропуск готовых тикетов

Issue, созданные через `to-tickets`, уже имеют метку `ready-for-agent` и **не проходят** повторный триаж. Автотриаж срабатывает только на входящие обращения без меток.

### Где смотреть результаты

- **GitHub Actions**: вкладка [Actions → auto-triage](https://github.com/NelyaShaihutdinova/ai-for-developers-project-387/actions/workflows/auto-triage.yml)
- **Комментарий в issue**: агент публикует разбор с вопросами и рекомендациями

### Параметры

| Параметр | Значение |
|---|---|
| **Событие** | `issues:opened` |
| **Prompt** | Встроенная инструкция `/triage` — анализ, вопросы, рекомендации |
| **Таймаут** | 10 минут |
| **Параллельность** | Один запуск на issue (`cancel-in-progress: false`) |
| **Фильтр авторов** | `author_association != 'NONE'` (исключает fork) |
| **Фильтр ботов** | `user.type != 'Bot'` |

## Автопроверка PR (Auto-Review)

При каждом pull_request (opened, synchronize) запускается `auto-review.yml`. Агент читает `REVIEW.md`, проверяет критерии календаря (бронирование, API, контрактная цепочка, фронтенд, БД, безопасность, conventional commits) и оставляет развёрнутый комментарий-ревью.

### Параметры

| Параметр | Значение |
|---|---|
| **Событие** | `pull_request` (opened, synchronize) |
| **Критерии** | `REVIEW.md` — чек-лист календаря бронирований |
| **Таймаут** | 10 минут |
| **Параллельность** | Один запуск на PR (`cancel-in-progress: true`) |
| **Фильтр веток** | `head.repo.full_name == base.repo.full_name` (только свой репо, боты разрешены) |
| **Права** | `contents: read`, `pull-requests: write` |

### Шаблон PR

`.github/pull_request_template.md` содержит разделы: проверки (команды, ссылки, SHA), оценка риска, способ отката.

## Лимит запусков агента

Для предотвращения бесконечных вызовов агента установлен лимит **3 запуска** на один PR/issue.

### Как работает

1. Счётчик хранится в **GitHub Actions API** (история workflow runs) — токен агента не может его переписать
2. Перед вызовом модели шаг `Check run limit` подсчитывает completed runs для данного PR/issue
3. При `completed_runs >= MAX_RUNS` модель **не вызывается**, публикуется комментарий с reason

### Reason коды

| Код | Описание |
|---|---|
| `timeout` | Предыдущий run отменён по таймауту |
| `infra` | Сбой инфраструктуры (OIDC, API-ключ, секреты) |
| `agent_failed` | Агент завершился с ошибкой (не infra) |
| `limit_exhausted` | Лимит превышен, но нет данных о последнем run |

### Где смотреть

- Комментарий в PR/issue: `⛔ Agent run limit exhausted (N/3)` с reason, SHA и ссылкой на логи
- GitHub Actions: вкладка [Actions](https://github.com/NelyaShaihutdinova/ai-for-developers-project-387/actions) — история запусков

## Аудит

Ежедневный аудит репозитория через OpenCode-агента.

### Как работает

1. Воркфлоу `audit.yml` запускается по cron или вручную
2. Агент проверяет: безопасность, stale branches, CI failures, stale issues/PRs, Conventional Commits, зависимости, актуальность инструкций
3. Для каждой проблемы создаётся issue с лейблом `audit`
4. Дубликаты пропускаются

## Lighthouse-аудит

Еженедельная проверка производительности приложения через Lighthouse.

### Как работает

1. Воркфлоу `lighthouse-audit.yml` запускается по понедельникам в 06:30 MSK или вручную
2. Разбудит Render-приложение (до 10 попыток с интервалом 15с)
3. Запускает Lighthouse CI (3 прохода) по `APP_URL`
4. Сохраняет отчёт как артефакт (30 дней)
5. Агент анализирует отчёт и создаёт issues с лейблом `lighthouse` **только для новых проблем**

### Настройки

- `APP_URL` — Repository Variable (Settings → Actions → Variables)
- `lh-budget.json` — бюджет: total < 500KB, FCP < 3s, TTI < 10s

### Где смотреть

- **GitHub Actions**: [Actions → lighthouse-audit](https://github.com/NelyaShaihutdinova/ai-for-developers-project-387/actions/workflows/lighthouse-audit.yml)
- **Артефакты**: вкладка Artifacts каждого запуска (`.lighthouseci/`, 30 дней)
- **Публичные отчёты**: ссылки в summary (temporaryPublicStorage)
- **Результаты**: [Issues с лейблом `lighthouse`](https://github.com/NelyaShaihutdinova/ai-for-developers-project-387/issues?q=label%3Alighthouse)

## Выводы о работе GitHub-агента

### Что потребовало уточнений

1. **`persist-credentials: false` блокировало `git push`** — агент делал коммиты, но не мог запушить ветку. Исправлено на `true` для workflow `opencode.yml`.
2. **`contents: read` не давало создавать PR** — `gh pr create` требует `contents: write` и `pull-requests: write`.
3. **Агент не прогоняет Prettier** — после реализации файлы были не отформатированы. CI падал на `format:check`.
4. **Агент добавляет unused imports** — `within` из `@testing-library/react` попал в тест без использования. ESLint ловил это на CI.
5. **Debug-строки в логах** — `echo "KEY_LENGTH=..."` попало в финальный коммит.
6. **Счётчик лимитов считал предыдущие тестовые запуски** — issue #10 исчерпал лимит (3) ещё до implement-spec. Лимит работает корректно, но нужно создавать свежий issue для новых задач.

### Что изменила в настройках

| Настройка | Было | Стало | Причина |
|---|---|---|---|
| `persist-credentials` | `false` | `true` (opencode.yml) | Агент не мог `git push` |
| `permissions: contents` | `read` | `write` (opencode.yml) | Агент не мог `gh pr create` |
| `permissions: pull-requests` | — | `write` (opencode.yml) | Создание PR |
| `opencode.jsonc` | — | `external_directory: "*-wt-*": "allow"` | implement-spec создаёт worktree |
| Авторевью: событие | `anomalyco/opencode/github` action | `opencode run --format json` (CLI) | Action проверяет права отправителя → `permission: none` для ботов |
| Авторевью: `author_association` | `!= 'NONE'` | Убран (auto-review.yml) | Боты имеют `NONE`, но из своего репо — должны получать ревью |
| GitHub Actions: approval | `Require approval for first-time contributors` | `Require approval for first-time contributors who are new to GitHub` | release-please и opencode-agent не должны ждать аппрува |
| Лимит запусков | — | 3 на PR/issue | Защита от бесконечных вызовов |

### Что работает без вмешательства

- Триаж новых issue (`auto-triage.yml`) — задаёт вопросы, применяет метки
- Реализация по спецификации (`implement-spec`) — создаёт ветку, коммиты, PR
- Лимит запусков — после 3 вызовов `/oc` завершается без модели
- Авто-ревью на каждый PR — читает REVIEW.md, комментирует diff
- Аудит репозитория — проверяет CI, stale issues, формат коммитов
